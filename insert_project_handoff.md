## 5. Bug History (why the "missing" count kept dropping — important context, don't be surprised if it drops again)

The reconciliation numbers changed dramatically across the conversation as each of these was found and fixed, **in this order**:

1. **Character-similarity collisions.** Raw `difflib.SequenceMatcher` similarity on full normalized names failed badly because Jordanian legislative titles reuse heavy boilerplate ("قانون معدل رقم X لسنة Y..."). Fixed by switching to **content-word Jaccard similarity** (`content_similarity()` in `lib_matching.py`): strip a curated list of legislative "stopwords" (قانون, رقم, لسنة, معدل, مؤقت, تعديل, etc. — built by normalizing the raw words the same way input text is normalized, to avoid diacritic/hamza-mismatch bugs) and compare the remaining content words via Jaccard.
2. **Tier 2 (year + magazine number, used when `Law_Number` is blank) trust level oscillated**: first over-trusted, then over-rejected (based on a too-small sample), then properly recalibrated into a tiered-confidence system (auto-accept above a high-confidence threshold, flag for review in a middle band, reject near zero).
3. **CSV chain-structure bug.** Rows added to the CSV via a prior "editorial recovery" effort (tagged `"مضاف من ملف المحررين"` / `"مسترجَع من عمل الفريق السابق"` / match-tier `"name_only"` in extra CSV columns) frequently have **wrong `chain_id_v2`/`chain_position_v2`**: an amendment is sometimes tagged `chain_position_v2=0` (treated as its own standalone base law) instead of nested under its true parent, or nested under the *wrong* parent chain entirely (e.g., a 1971 amendment attached to a 1999 law's chain). `step1`'s original design trusted this chain structure and only ever checked an item against the *one* pool implied by its assumed type/parent — so misclassified items were invisibly missed. Fixed by `step9`'s comprehensive re-check.
4. **Genuine literal duplicate content inside the JSON itself.** Some amendments appear **verbatim identically** (same name, number, year, *and* magazine number) nested under 2, or even 4, different top-level parent laws. `match_one()`'s Tier-1 collision resolver originally required a clear score margin between the best and second-best candidate to accept a match, or a unique magazine-number match — both checks failed when multiple candidates were *all* perfectly identical, causing a real "already exists" case to be wrongly rejected as "ambiguous, can't resolve." Fixed in `lib_matching.py` v1.5.0: if magazine-based disambiguation also can't separate them (checked *first*, since it's more precise when it *can* differentiate — see the ordering-bug note below), and the top candidates are near-identical (≥0.90 similarity), accept the match — it doesn't matter which literal copy is "the" match since the content demonstrably already exists.
   - **A sub-bug found while building the above fix:** the initial version of this fix checked "near-identical duplicates" *before* attempting magazine-based tiebreak, which caused it to pick an arbitrary duplicate even in cases where the magazine number *could* have precisely distinguished two genuinely-different same-named entries (e.g., two different "budget supplement" laws from 1956 that share a name template but have different magazine numbers). Fixed by reordering: magazine-tiebreak is always tried first; the "near-identical, doesn't matter which" acceptance is the last resort.
5. **Items typed as "amendment" were never checked against the top-level pool at all.** Even after fixing the chain-structure bug's *symptom* (misassigned parent), `step8`/`step9`'s initial re-check logic only searched the flattened *amendments* pool for anything not already matched — it never re-attempted a search of the *top-level laws* pool for items assumed to be amendments. Since the JSON frequently has entries with a **blank `Leg_Number` field**, and Tier 1 (which requires an exact number match) can never bridge that gap, many genuinely-present top-level laws were permanently missed for any CSV row that happened to be typed "amendment." Fixed in `step9` v2.0.0 by checking **both pools** for every single item, regardless of its assumed CSV type.
6. **Tier 2's magazine-number collision bug (the most recent, and arguably most consequential, fix).** `Magazine_Number` is **not a unique identifier** — it's a gazette issue number, and it is completely normal for several unrelated laws to be published in the same issue (a real example found: **5 different, unrelated laws** all sharing magazine number 414 for year 1933). The old Tier 2 code took the **first** candidate in iteration order whose magazine number matched and returned immediately, without checking whether a *better* content match existed among other candidates sharing that same magazine number later in the list. Fixed in `lib_matching.py` v1.6.0: Tier 2 now collects **all** magazine-matching candidates for the year and picks the one with the best content-similarity score among them (same philosophy as the Tier-1 collision resolver). This single fix alone dropped the "confirmed missing" count from 272 to 246, and dropped the "zero articles extracted" count from 38 to 13.

**Running total of the "confirmed genuinely missing" count as each bug was fixed:** 608 → 344 (chain-structure fix) → 341 (duplicate-content fix) → 272 (dual-pool fix) → **246** (Tier-2 magazine-collision fix, current as of the last message in this conversation).

**Given this history, do not assume the current numbers are final.** If more bugs of a similarly subtle nature turn up, that would be consistent with the pattern so far, not surprising. Always re-verify with real data before treating a number as authoritative.

## 6. The Matching Algorithm (`lib_matching.py`, current v1.6.0)

- **`normalize_arabic_name()`**: normalizes Arabic text (unify alef/hamza/taa-marbuta forms, strip diacritics/tatweel, strip punctuation, collapse whitespace) for comparison.
- **`normalize_number()` / `normalize_year()`**: strip a spurious trailing `.0` (from CSV float-formatted export) and leading zeros; return `None` for blank.
- **`content_similarity(a_norm, b_norm)`**: Jaccard similarity over "content words" — i.e., words remaining after removing a small set of legislative-boilerplate stopwords (normalized the same way as input text) and stripping the leading Arabic definite article (`ال`) from each remaining word. This is the core similarity metric used everywhere; **raw character similarity is not used for any matching decision** (only kept as a vestigial, unused function).
- **`match_one(number, year, name_norm, magazine_number, magazine_page, pool_by_num_year, pool_by_year)`** tries, in order:
  - **Tier 1** — exact `(number, year)` key lookup in `pool_by_num_year`. If exactly one candidate: accept if content similarity is above a low floor (~0.10, tuned against real true/false examples), with a "needs confirmation" flag below a higher confidence floor (~0.50). If it's a collision (multiple candidates share the same `(number, year)`): try to resolve by (a) a clear content-similarity margin between best and second-best, else (b) magazine-number-based tiebreak among the colliding candidates (requires the disambiguating name similarity to also clear a low floor, to avoid trusting a magazine-number coincidence between two genuinely unrelated laws), else (c) accept anyway if the top candidates are near-identical to each other (≥0.90 similarity — the "genuine duplicate content" case), else mark ambiguous/unresolved (and record all colliding candidate names + magazine numbers for human review).
  - **Tier 2** — for when `number` is blank (or Tier 1's key didn't exist): among all candidates sharing the given `year`, collect **all** whose `magazine_number` (and optionally `magazine_page`) matches, then pick the best content-similarity match among *that whole group* (not just the first found — this was the v1.6.0 fix).
  - **Tier 3** — last resort: best content-similarity match anywhere in the same `year`, accepted only above a stricter threshold (~0.45), always flagged for human confirmation (no number or magazine anchor at all).
- **Building the two search pools:**
  - "Top-level pool": one `Candidate` per JSON top-level entry.
  - "Global amendment pool": one `Candidate` per `Mod_Legs[]` entry, flattened across **every** top-level entry (tagged with a `ref_id` like `mod:{top_index}:{mod_index}` so the true parent can be recovered).
  - **Both pools must be checked for every item**, regardless of what the CSV's chain structure claims the item "is" (see bug #5/#6 above).
